# Production Deployment on Main Branch with Single-AZ RDS MySQL and 100% Free Tier Compliance

Status: ready-for-agent

## Problem Statement

While the staging environment successfully validates continuous delivery pipelines using an ephemeral database container sidecar that resets on every task restart, a production environment on the primary release branch requires durable relational data storage that survives container restarts, deployments, and cost-control cycles. However, provisioning a traditional multi-zone production database, NAT gateways, duplicate container registries, and redundant account budgets immediately violates strict zero-cost cloud constraints by exceeding free-tier allowances. Furthermore, blindly applying staging's destruction-based hibernation to production would permanently erase customer and operational database records, while pushing frequent staging images to a shared registry with an undifferentiated retention rule risks evicting active production container images.

## Solution

Deliver a production deployment architecture and continuous delivery pipeline triggered from the primary release branch that pairs stateless container compute and load balancing with a persistent, Single-AZ managed MySQL relational database inside isolated private database subnets—engineered to operate strictly within 100% free-tier and promotional credit boundaries.

To protect both data durability and zero-cost operation, the production environment reuses account-wide singleton foundations (remote state storage, state locking, OIDC identity provider, account-wide cost budget, and container image registries with environment-prefixed retention rules) while isolating networking, load balancing, compute clusters, and secret parameters. The multi-mode lifecycle controller is extended to become environment-aware:
1. **Pause**: Scales production compute tasks to zero while keeping the load balancer and managed database active for sub-minute recovery.
2. **Hibernate**: Dismantles stateless hourly-billed routing and compute components (the load balancer, target groups, and container services) while suspending the persistent relational database in place (stopping the database instance without deleting its storage volume), reducing active compute and load-balancing spend to zero without data loss.
3. **Resume**: Inspects the surviving production infrastructure, automatically starts the managed database if suspended and waits for availability, reconstructs or scales up routing and compute components, and performs Dynamic DNS Binding to publish persistent and fallback URLs.

## User Stories

1. As a system administrator deploying the production release branch, I want relational data stored in a managed MySQL database instance rather than an ephemeral container sidecar, so that member records, subscriptions, and POS orders persist across container restarts and deployments.
2. As a project owner operating under strict zero-cost constraints, I want the managed relational database provisioned as a Single-AZ micro instance with 20 GB general-purpose SSD storage, disabled storage autoscaling, disabled performance insights, and a 7-day backup retention window, so that database usage stays 100% within the 12-month free-tier allowance.
3. As a security-conscious engineer, I want the production database placed in isolated private subnets with public accessibility disabled and no NAT gateway attached, so that the database is unreachable from the public internet while incurring zero NAT gateway or public IPv4 charges.
4. As a backend service running in a public subnet, I want the database security group to permit inbound MySQL traffic exclusively from the production container security group over internal VPC routing, so that application containers can query the database securely at zero network transit cost.
5. As a cloud architect optimizing container compute resources, I want the production backend task definition to omit the MySQL sidecar container and downsize task allocation to 256 CPU units and 512 MiB memory when external RDS mode is enabled, so that production container compute footprint is minimized by up to 75% compared to staging.
6. As a DevOps engineer maintaining staging and production in the same cloud account, I want the existing container module to retain the ephemeral MySQL sidecar by default when the external database flag is not set, so that staging continues operating unchanged without regressions.
7. As a DevOps engineer managing container images within a 500 MB free-tier registry quota, I want production and staging to share the same backend and frontend image repositories using environment-prefixed tags and tag-aware lifecycle retention rules, so that frequent staging builds never evict active production images and total storage remains within free limits.
8. As an infrastructure engineer applying configuration for production, I want the production environment to reference the existing account-level OIDC provider and container repositories via data lookups rather than attempting to recreate them, so that deployment provisioning never fails with duplicate entity errors.
9. As a project owner avoiding hidden billing charges, I want the production environment to rely on the existing account-wide monthly cost budget rather than creating a third budget resource, so that the account stays within the two-budget free-tier ceiling.
10. As a backend application running in the production profile, I want JDBC connections configured with preferred TLS encryption, a reduced connection pool size (maximum 10 connections, minimum 2 idle), disabled SQL debug logging, and initial schema plus demo seed migrations enabled, so that the micro RDS instance is protected from connection exhaustion, CloudWatch log ingestion stays within the 5 GB free tier, and the live production system is immediately ready for demonstration.
11. As a release engineer merging code into the main branch, I want an automated production continuous delivery pipeline that validates infrastructure code, builds and pushes production-tagged container images, and updates production task definitions, so that releases are delivered reproducibly without manual image builds.
12. As a release engineer merging code into the main branch while production is in Hibernate, I want the production continuous delivery pipeline to detect that container services are absent or inactive and gracefully skip service updates with a summary notice, so that merges do not fail or accidentally wake hibernated resources.
13. As a project owner pausing production for a short break, I want to trigger the Pause action targeting the production environment, so that frontend and backend tasks scale to zero while the load balancer and RDS instance remain warm for rapid recovery.
14. As a project owner hibernating production overnight or between demonstrations, I want the Hibernate action targeting production to destroy only the load balancer and container services while issuing a stop command to the RDS database instance, so that hourly compute and load balancer charges drop to zero while 100% of production database data is preserved.
15. As a developer executing Resume on a hibernated production environment, I want the workflow to automatically detect if the RDS database instance is stopped, start it, and wait until the database reaches an available state before starting application containers, so that backend startup and Flyway validation never fail due to an offline database.
16. As a developer executing Resume on the production environment, I want Dynamic DNS Binding to resolve the active production load balancer IPv4 address and update the configured production DuckDNS domain (with automatic fallback to the default DuckDNS domain secret), so that end users and evaluators have a stable access URL alongside the raw load balancer fallback link.
17. As a quality assurance engineer running automated infrastructure verification, I want comprehensive unit tests validating the production environment topology, RDS free-tier constraints, conditional sidecar removal, production Spring profile settings, and multi-environment lifecycle workflows, so that any configuration drift or free-tier violation is caught in CI before deployment.

## Implementation Decisions

- **Single-AZ Free-Tier Relational Database Module**: A dedicated database infrastructure module provisions a MySQL 8.4 instance sized to a free-tier micro instance class (`db.t4g.micro`), configured with 20 GB `gp2` storage, storage autoscaling disabled (`max_allocated_storage` set to `0`), `multi_az` disabled, `publicly_accessible` disabled, 7-day automated backup retention, performance insights disabled, and final snapshot skipped for clean teardown if ever needed.
- **Isolated Database Subnets without NAT Gateways**: The networking module is extended to optionally provision two private isolated database subnets across distinct availability zones with an internal-only route table, a database subnet group, and a dedicated database security group allowing inbound port 3306 traffic solely from the container task security group.
- **Conditional Sidecar Parameterization in Container Module**: The container orchestration module accepts an `enable_mysql_sidecar` boolean toggle (defaulting to `true` for backward compatibility with staging), a `db_host` address parameter, a `db_username` parameter, and a `spring_profile` parameter. When `enable_mysql_sidecar` is `false`, the backend task definition omits the sidecar container definition and health-check dependency, injects the external RDS endpoint into `DB_HOST`, and sets `SPRING_PROFILES_ACTIVE` to `prod`.
- **Shared Account Singletons vs. Isolated Environment State**: The production environment configuration stores its state under a dedicated `prod/terraform.tfstate` key within the existing remote state bucket and lock table. It isolates VPC CIDR blocks (`10.1.0.0/16`), load balancers, clusters, and SSM parameter namespaces (`/gym/prod/...`), while referencing the shared container repositories via data sources, reusing the existing OIDC provider (extended with RDS describe/start/stop permissions), and omitting a duplicate AWS Budget resource to respect the two-budget free-tier limit.
- **Environment-Prefixed Image Tagging and Lifecycle Isolation**: Production continuous delivery tags images with `prod-<sha>` and `prod-latest`, while staging uses `staging` / commit tags. Container registry lifecycle policies are structured so that staging image pushes cannot expire active `prod-*` images while keeping total stored images per repository within the 500 MB free-tier storage cap.
- **Production Application Profile Optimization**: A dedicated `prod` application configuration profile activates on `SPRING_PROFILES_ACTIVE=prod`. It configures JDBC with `sslMode=PREFERRED`, tunes HikariCP to `maximum-pool-size: 10` and `minimum-idle: 2` for micro instance memory limits, disables verbose Hibernate SQL logging (`show-sql: false`, `WARN`/`INFO` levels) to conserve the 5 GB CloudWatch Logs free tier, and retains both core schema migrations and initial demo seed migrations so the production deployment is immediately usable upon first boot.
- **Production Continuous Delivery Pipeline**: A dedicated production deployment workflow triggers on pushes to `main` and manual dispatch. It validates production infrastructure definitions, builds and pushes backend and frontend images with `prod-` tags in parallel, registers updated task definitions, and conditionally updates active ECS services or logs a hibernation notice when services are scaled down or dismantled.
- **Environment-Aware Lifecycle Controller (`Pause` / `Hibernate` / `Resume`)**: The infrastructure control workflow accepts an `environment` choice input (`staging` or `prod`, defaulting to `staging`). When `prod` is selected:
  - `Pause` scales production backend and frontend services to `0` while leaving the load balancer and RDS instance running.
  - `Hibernate` runs targeted Terraform destruction against the production load balancer and ECS services, and executes an AWS CLI command to stop the production RDS instance if it is currently available.
  - `Resume` checks the RDS instance status first (starting it and waiting for `db-instance-available` if stopped), then inspects load balancer existence to either scale ECS services to `1` (fast path from Pause) or run `terraform apply` to reconstruct the load balancer and services (full recovery from Hibernate), followed by Dynamic DNS Binding to DuckDNS.

## Testing Decisions

- **Good Test Principle**: Tests must assert observable infrastructure contracts, security boundaries, free-tier guardrails, and workflow behavioral guarantees (such as single-AZ enforcement, absence of public database exposure, conditional removal of sidecar containers, and RDS stop/start orchestration during hibernation) without coupling to fragile formatting details or requiring live AWS cloud credentials during unit test execution.
- **Tested Seams**:
  - **Seam 1 — Infrastructure & Module Contract Suite (Python `unittest` suite)**: Validates the RDS module free-tier invariants, networking isolated database subnet and security group rules, ECS conditional sidecar toggle, and production environment composition (`infra/environments/prod`), while ensuring all existing staging infrastructure unit tests continue to pass without modification.
  - **Seam 2 — CI/CD & Lifecycle Workflow Contract Suite (Python `unittest` suite)**: Validates the production deployment pipeline (`cd-prod.yml` trigger on `main`, `prod-` image tagging, graceful hibernate bypass) and the multi-environment `infra-control.yml` workflow (`environment` selector, RDS `stop-db-instance` on hibernate, RDS `start-db-instance` + wait on resume, and DuckDNS binding).
  - **Seam 3 — Backend Production Profile Configuration Contract**: Validates that the `prod` Spring Boot configuration profile defines safe connection pool bounds, disables verbose SQL logging, and configures Flyway migration locations accurately.
- **Prior Art**: The existing Python infrastructure test suite (`test_networking_and_alb.py`, `test_ecr_and_cd.py`, `test_ecs_and_cd_deployment.py`, `test_cost_monitoring_and_task_def.py`, `test_cloudwatch_logging.py`, and `test_infra_control.py`) establishes the pattern of inspecting Terraform configurations and GitHub Actions workflows at the module and workflow boundary.

## Out of Scope

- Multi-AZ database deployment or read replicas (excluded to maintain 100% RDS free-tier compliance as documented in ADR 0003).
- NAT Gateway or VPC Interface Endpoints provisioning (excluded because they incur immediate hourly AWS charges with no free tier).
- Route 53 hosted zones or paid custom domains (DuckDNS Dynamic DNS Binding and raw ALB URLs remain the zero-cost access layer).
- Automated database snapshot restoration workflows (stopping RDS in place preserves the 20 GB volume across hibernation cycles without requiring snapshot teardown/restore).
